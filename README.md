# SPECTRA — AI Media Forensics Workstation

SPECTRA is a web-based image-analysis workstation designed to support preliminary assessment of AI-generated versus human-created images. It combines a multi-page forensic-style interface, a Node.js/Express application server, and a Python FastAPI inference service backed by a Hugging Face image-classification model.

The project brings together image ingestion, SHA-256 hashing, basic metadata inspection, asynchronous analysis jobs, result review, and downloadable investigation records in one workflow.

> **Important limitation:** SPECTRA is an experimental decision-support and educational project, not a validated forensic instrument. Its classifier returns model estimates, not proof of authenticity or authorship. Do not use a model verdict as the sole basis for legal, disciplinary, journalistic, financial, or other high-impact decisions.

## Overview

Digital images can be created, edited, recompressed, or generated by AI tools. SPECTRA provides a single interface for examining image files and viewing an AI classifier's estimate alongside basic file-integrity information.

The application currently has two distinct responsibilities:

1. **Application and presentation layer:** receives uploads, creates jobs, calculates file hashes, extracts limited metadata indicators, exposes job/report endpoints, and serves the interface.
2. **Inference layer:** decodes and normalizes the uploaded image, runs the configured Transformers image-classification pipeline, and returns model labels and scores.

These layers are separate processes and can run on different ports or hosts. The Node.js service calls the Python service over HTTP.

## Problem Statement

The volume of synthetic and manipulated imagery makes preliminary media assessment increasingly useful. However, an image classifier alone cannot conclusively establish whether an image is authentic, who created it, or whether it has been manipulated.

SPECTRA aims to make an initial review workflow more organized by combining:

- A model-based AI-versus-human image classification estimate.
- A SHA-256 digest for identifying the exact uploaded file bytes.
- Basic image properties and limited metadata-marker inspection.
- A job-based user interface for viewing progress and results.
- Exportable text reports and a browser-side investigation ledger.

The intended result is a **preliminary assessment workflow**, not a replacement for expert forensic examination.

## How It Works

### 1. Image ingestion

A user selects or drops an image in the analysis interface. The browser submits it to the Node.js endpoint `POST /api/analyze` using multipart form data.

The application accepts these filename extensions:

- `.jpg`
- `.jpeg`
- `.png`
- `.webp`

The upload limit configured in the Node.js application is 20 MB.

### 2. Job creation

The Node.js server creates a unique job ID and stores the job in an in-memory map. It returns HTTP 202 with the ID and a queued status, then starts processing in the background.

### 3. File inspection

The application attempts to determine the image dimensions and format, computes a SHA-256 digest over the uploaded bytes, and performs a limited scan for selected metadata markers.

The digest is based on the uploaded byte stream. It can help compare copies of the same file, but it does not prove where the image originated or whether its content is truthful.

### 4. Model inference

The Node.js service sends the image to the Python backend at `POST /api/classify`. The Python service decodes the file with Pillow, applies EXIF orientation where possible, converts it to RGB, and invokes the configured Transformers image-classification pipeline.

The configured model is:

`Ateeqq/ai-vs-human-image-detector`

The Python implementation currently configures CPU inference (`device=-1`). The first model download and load can take time, depending on the machine and network.

### 5. Verdict estimate

The current application uses a 0.70 threshold:

- **AI-Generated:** the mapped AI score is at least 70%.
- **Human-Created:** the mapped human score is at least 70%.
- **Inconclusive:** neither mapped score reaches 70%.

These labels are model outputs under a chosen decision rule. Scores must not be interpreted as calibrated probabilities or conclusive forensic evidence. The inference code maps model labels to AI/human categories; any unrecognized labels should be reviewed because they can affect the derived scores.

### 6. Results and reporting

The interface polls the job endpoint to update its progress. It can display the file's properties, hash, model findings, and limitations. The application also exposes a text-report endpoint for completed jobs and a history endpoint for the in-memory job list. The browser ledger stores sanitized metadata in local storage.

## Architecture

```text
Browser
  |
  | HTML pages, CSS, JavaScript
  | POST /api/analyze
  v
Node.js + Express (server.ts)
  |
  | creates in-memory job
  | computes SHA-256
  | inspects basic image metadata
  |
  | POST /api/classify
  v
Python + FastAPI (server.py)
  |
  | Pillow decode / EXIF orientation / RGB conversion
  | Hugging Face Transformers pipeline
  v
Ateeqq/ai-vs-human-image-detector
  |
  | labels and scores
  v
Python response -> Node job state -> Browser UI

Browser ledger: localStorage (metadata records)
Server jobs: process memory (job status and temporary image bytes)
```

### Important deployment detail

There are two different server processes:

- The **Node.js server** serves the interface and the public application API. Its default port is 3000.
- The **Python FastAPI server** provides the classifier service. Its local default port is 8000. The Dockerfile for the Python service defaults to 8080 for container deployment.

The `PYTHON_BACKEND_URL` variable must point to the Python service's reachable base URL. The Python service must not be assumed to be available merely because the Node.js server has started.

## Prerequisites

For the local two-service setup, install:

- Git.
- Node.js 22 or another Node.js version compatible with the project's TypeScript and runtime dependencies.
- Bun, to use the repository's `bun.lock`, or npm if you install dependencies using `package.json`.
- Python 3.11 recommended for consistency with the provided Dockerfile.
- pip and Python virtual-environment support.
- Internet access for the initial Hugging Face model download and for any external frontend assets still loaded via CDN.

The classifier uses PyTorch and Transformers. CPU inference is configured in the code. Actual memory needs depend on the model version, image dimensions, and runtime environment.

## Local Setup

### 1. Clone the repository

```bash
git clone https://github.com/asrxznc/Spectra.git
cd Spectra
```

### 2. Install Node.js dependencies

Using Bun:

```bash
bun install --frozen-lockfile
```

Or using npm:

```bash
npm install
```

The repository includes a Bun lockfile, not an npm package lockfile. If reproducible npm installs are desired, commit a `package-lock.json` generated and reviewed by the project maintainers.

### 3. Create the Python environment

Linux/macOS:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
```

Windows PowerShell:

```powershell
py -3.11 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
```

PyTorch wheels and their platform requirements vary. If installation fails, consult the official PyTorch installation selector for your operating system and Python version before manually changing dependency versions.

### 4. Configure the Node.js service

Create a local environment file:

```bash
cp .env.example .env
```

For Windows Command Prompt:

```bat
copy .env.example .env
```

Use the following local configuration:

```dotenv
PORT=3000
PYTHON_BACKEND_URL=http://127.0.0.1:8000
```

The Node.js server reads the `.env` file itself, so a separate dotenv package is not required by the current implementation.

### 5. Start the Python inference service

From the repository root, with the Python virtual environment activated:

```bash
uvicorn server:app --host 127.0.0.1 --port 8000
```

On startup, the application starts loading the Hugging Face model in a background thread. Wait until the health endpoint reports that the model is loaded before testing classification.

Check:

```bash
curl http://127.0.0.1:8000/api/health
```

On Windows, you can open that URL in a browser instead of using `curl`.

### 6. Start the Node.js server

In a separate terminal, from the repository root:

```bash
npm run dev
```

Or, if using Bun to run the package scripts:

```bash
bun run dev
```

Open [http://localhost:3000](http://localhost:3000).

**Keep both services running.** If the Python backend is not reachable, the interface may load but analysis will fail or show a degraded classifier state.

## HTTP API Reference

The following endpoints are implemented in `server.ts`, unless explicitly identified as Python inference endpoints. Examples assume a local Node.js URL of `http://127.0.0.1:3000`.

### Node.js application endpoints

| Method | Endpoint | Purpose |
|---|---|---|
| `GET` | `/api/health` | Reports application and classifier readiness |
| `POST` | `/api/analyze` | Accepts multipart image field `file` and creates an analysis job |
| `GET` | `/api/jobs/:id` | Returns the job state and findings |
| `GET` | `/api/jobs/:id/image` | Returns the temporarily retained image bytes |
| `POST` | `/api/jobs/:id/retry` | Retries a job while its image bytes remain in memory |
| `GET` | `/api/history` | Returns in-memory jobs and aggregate statistics |
| `GET` | `/api/reports/:id` | Downloads a text report for a completed job |

Example upload:

```bash
curl -X POST \
  -F "file=@./sample.jpg" \
  http://127.0.0.1:3000/api/analyze
```

A successful submission returns HTTP 202 and a JSON object containing a `job_id` and `status`. Use the returned ID with `GET /api/jobs/:id` to track processing.

Example status request:

```bash
curl http://127.0.0.1:3000/api/jobs/YOUR_JOB_ID
```

Example report download:

```bash
curl -OJ http://127.0.0.1:3000/api/reports/YOUR_JOB_ID
```

### Python inference endpoints

| Method | Endpoint | Purpose |
|---|---|---|
| `GET` | `/api/health` | Reports the model identifier, load state, and any cached loading error |
| `POST` | `/api/classify` | Accepts multipart image field `file`, preprocesses it, and returns classifier output |

Example direct inference upload:

```bash
curl -X POST \
  -F "file=@./sample.jpg" \
  http://127.0.0.1:8000/api/classify
```

The Python response includes a `result` object containing the verdict estimate, score fields, raw model labels, threshold, model ID, and limitation disclaimer.

## Classification Logic

The inference service runs a Hugging Face Transformers `image-classification` pipeline using the configured model. The Python code requests CPU execution and loads the pipeline during application startup.

The mapping logic recognizes a set of strings for AI-related and human-related classes. It then evaluates the mapped scores against a 0.70 threshold.

This is a basic decision rule, with several implications:

- Scores from a neural classifier are not automatically calibrated probabilities.
- A model may produce labels other than the names expected by the mapping code.
- The human score has a fallback derived from the AI score, which should not be mistaken for a verified complementary probability distribution in every possible model-output case.
- Model performance can shift across image sources, editing pipelines, image quality, and newer generative systems.
- The repository does not itself demonstrate an independently evaluated accuracy, precision, recall, calibration curve, or false-positive rate for the integrated model.

Any benchmark claims should be added only after testing on a documented dataset that is separate from model training data.

## Integrity and Metadata Notes

### SHA-256

SPECTRA calculates SHA-256 on the uploaded file bytes. It can establish whether two available byte streams are identical by comparing their digests. It does not establish the original creator, creation time, camera, or authenticity of image content.

### EXIF and PNG metadata

The current Node.js implementation performs a limited marker scan:

- For JPEG files, it looks for an APP1 marker and checks whether an EXIF header is present.
- For PNG files, it checks for text-related chunk markers and selected prompt-related strings.

This is **not a complete EXIF parser or comprehensive metadata-forensics engine**. Metadata can be absent, stripped, edited, or forged. A marker's presence or absence should not be treated as conclusive evidence.

### Reports

The text report combines job details, digest, image properties, model score estimates, raw labels, metadata markers, and a limitation disclaimer. The report is generated by the Node.js process from the current in-memory job state.

The existence of an exportable report does not by itself make the record a legally defensible chain-of-custody artifact.

## Data Retention and Privacy

The application currently uses more than one storage mechanism:

- **Node.js process memory:** stores job state and temporary image bytes.
- **Browser localStorage:** stores sanitized record metadata without the image payload.
- **No database service is configured** in the current repository.

The application code uses a 24-hour timestamp-based expiry policy for server jobs and browser-side ledger entries. This is application-level cleanup, not guaranteed durable retention or secure deletion. Server restarts remove in-memory jobs; browser records may remain separately until cleaned, deleted by the user, or removed by browser storage policies.

The default configuration is not a multi-user storage architecture. No authentication or per-user authorization layer is present in the inspected API routes. Do not expose this deployment publicly with unrestricted uploads or access to job IDs until suitable access controls and resource limits have been implemented.

Before analyzing sensitive material, review where the Node.js and Python services run, where image bytes travel, which browser or external assets are contacted, and how hosting logs and infrastructure retain data.

## Docker Deployment

The repository's `Dockerfile` builds the **Python inference service**. It does not, by itself, containerize the full two-service system or start `server.ts`.

The Dockerfile:

- Uses a Python 3.11 slim base image.
- Installs CPU-oriented PyTorch dependencies and the Python requirements.
- Preloads the configured model during the image build.
- Runs Uvicorn on port 8080 by default.
- Uses the Python health endpoint for a container health check.

Build and run the Python service:

```bash
docker build -t spectra-inference .
docker run --rm -p 8080:8080 spectra-inference
```

Check:

```bash
curl http://127.0.0.1:8080/api/health
```

When using this container with a Node.js process on the host machine, configure `PYTHON_BACKEND_URL` to a host-reachable URL for port 8080. When both services run in Docker, use the Python service's Compose service name rather than `127.0.0.1` from inside the Node.js container.

The Python container can be large because it includes machine-learning libraries and pretrained model weights. Confirm resource requirements and hosting limits before deployment. The image-build-time model download also means the build requires model access and can fail if the model or upstream dependencies are unavailable.

## Troubleshooting

### The web interface loads but analysis fails

1. Check `GET /api/health` on Node.js.
2. Check `GET /api/health` on Python.
3. Confirm `PYTHON_BACKEND_URL` points to the reachable Python service.
4. Confirm the model-loading status is `loaded`.
5. Inspect both processes' logs for model or request errors.

### The Python service does not start

Confirm that the virtual environment is active and that dependencies from `requirements.txt` installed successfully. PyTorch wheels are platform-specific; consult the official PyTorch installation selector if needed.

### The first analysis is slow

The model must download and initialize if it has not been cached. The application also uses short artificial delays for visible progress stages, in addition to actual inference time.

### A job cannot be found after restarting the service

Jobs and uploaded bytes are held in process memory. A restart clears that state. Browser-side metadata may still exist, but it does not recreate the missing server job or its image bytes.

### Report download fails

Reports are generated from the server's in-memory job object, and the job must be complete. A missing, expired, or post-restart job cannot produce a report through the current endpoint.

### The model never becomes ready

The current Python implementation stores its initial load error and does not automatically clear it for a later reload attempt. Restart the service after correcting the underlying model-loading problem, or implement an explicit, controlled retry mechanism.

## Known Limitations

- The classifier is a single-model heuristic and is not shown in this repository to be independently validated for forensic use.
- Image analysis is limited to the configured model's label space and preprocessing path.
- EXIF and PNG metadata inspection is intentionally basic.
- Jobs and image payloads are held in volatile server memory.
- Browser localStorage and server-side history can diverge.
- The current application API has no authentication or user-level authorization.
- Both Node.js and Python currently enable broad CORS settings.
- There is no configured persistent database, distributed job queue, or object storage.
- The provided Dockerfile covers Python inference, not the complete application.
- There is no test suite or CI workflow in the inspected repository tree.
- No open-source license file is present in the inspected root.
- Frontend pages load some libraries and design assets through external CDNs, so offline operation and strict content-security policies require additional work.

## Security Considerations

Before using SPECTRA with untrusted uploads or exposing it to the internet, prioritize the following:

1. **Authentication and authorization:** protect job, image, history, and report endpoints; make access checks per user rather than relying only on unpredictable IDs.
2. **Upload validation:** inspect actual file content and decoded dimensions, not just the supplied filename extension. Add request-rate, concurrency, pixel-count, and memory limits.
3. **CORS and HTTP security:** replace wildcard CORS with an explicit origin allowlist and add appropriate security headers.
4. **Resource protection:** limit simultaneous inference requests, cap model workload, and prevent excessive job creation.
5. **Data handling:** define retention, deletion, logging, and access policies for uploaded media and reports.
6. **Dependency hygiene:** scan and update Python and Node dependencies, pin tested versions for production, and review model-license and model-card requirements.
7. **Trust boundaries:** treat file metadata, filenames, model labels, and user-controlled inputs as untrusted data. Avoid inserting unescaped values into HTML.

## Testing and Validation

A useful validation suite should include:

- Valid JPEG, PNG, and WebP samples.
- Unsupported extensions, spoofed file extensions, corrupted images, and oversized uploads.
- Extremely wide/tall images and large pixel counts.
- Python service unavailable, model loading, model loading failure, inference timeout, and inference error cases.
- Correct SHA-256 calculation against a known test digest.
- Metadata-present, metadata-absent, and malformed metadata samples.
- Job retry, 24-hour expiry behavior, and server-restart behavior.
- Text report generation and CSV export.
- Two users or sessions attempting to access the same job.
- Benchmarking across multiple authentic-camera and AI-generated datasets, with documented dataset provenance and no train/test leakage.

Track precision, recall, false-positive rate, false-negative rate, calibration, latency, memory usage, and performance by image source. Never advertise an accuracy percentage until these tests have actually been run and their methodology is documented.

## Roadmap

Suggested development priorities:

### Reliability
- Add automated tests for image validation, hash generation, classification mapping, and report generation.
- Define typed API response schemas and centralize error handling.
- Add retryable model initialization with readiness states that reflect actual inference availability.

### Security
- Add authentication, authorization, rate limiting, safe upload validation, and explicit CORS configuration.
- Add production security headers and audit dependency vulnerabilities.
- Avoid serving private image payloads without an access check.

### Data architecture
- Move job state to a persistent database.
- Move uploads to private object storage with explicit retention/deletion policies.
- Use a queue or controlled worker pool for scalable inference.
- Define a single source of truth for the record ledger instead of merging client and server records ambiguously.

### Forensic capability
- Use a complete metadata parser and document its evidence limitations.
- Add cryptographic provenance checks such as supported C2PA manifests where appropriate.
- Treat model output as one signal among several, not as an authenticity certificate.
- Benchmark and calibrate the classifier on representative data and publish reproducible evaluation methods.

### Engineering quality
- Add CI for tests, type checks, linting, dependency scans, and container builds.
- Pin tested dependency versions and document supported runtime versions.
- Add deployment documentation for a full two-service setup.
- Add license, contribution guidelines, and a security-reporting policy.
